# 秘书 Agent 设计

> 状态：设计稿，未实现。取代未合入的项目级调度台（分支 `enso/020dc8e8`），不依赖 Bot 模式。不分期，一次合入，放在实验开关后。

## 目标

一个不属于任何项目的全局 agent，负责和用户对话，代为查看各项目与会话的状态、创建会话并派活、接收会话结果后转告用户。它自己不读写代码。

价值只在三点上成立，缺一个就退化成"带 delegate 的普通会话"：

1. 跨项目；
2. 派出的是用户随时可接手的**普通可见会话**；
3. 会话结果**主动回传**给秘书。

## 已定决策

| 问题 | 结论 |
| --- | --- |
| 与调度台关系 | 取代；调度台分支只作参考，不合入 |
| Bot 模式 | 不依赖、不复用成员档案 |
| 交付方式 | 不分期，一次合入；内部按「实现顺序」逐步提交，每步有自己的检查 |
| 可读的会话 | 全部，排除 child、bot、已归档 |
| 可发消息 / 停止的会话 | 只限秘书派出的，或用户在秘书会话里点名的；授权归秘书身份，不归单个秘书会话 |
| 秘书会话数量 | 多个；共享记忆、工作台与授权 |
| PWA 完整模式 | 必须可用 |
| SSH 项目 | 不支持派活，可读列表 |
| 自主度默认 | 派活前先问我；免确认只对用户勾选的项目生效 |
| 初次设置 | 表单或对话二选一；之后可修改，也可重来 |
| 记忆 | 秘书私有记忆可读写；各项目记忆与全局记忆只读 |
| 插件 | 全部关闭（工具、技能、MCP、hooks），与 Bot 会话同口径；定时由秘书自带，不依赖 scheduler 插件 |
| 定时 | 秘书自带 `schedule_*`，支持一次性时间与 cron，归属秘书身份 |
| 派出会话目标 | `session_create` 可带 `goal`，由 Main 驱动续跑直到完成 / 受阻 |
| 配置 CLI | 不接入 |

默认值（可后续调整）：派出会话默认不开独立 worktree，由秘书按任务或用户要求决定；`session_read` 默认返回摘要和最后 N 条消息，支持翻页；回传只在完成 / 失败 / 需要用户处理时触发；派出会话默认用目标项目的默认模型，秘书可显式指定。

## 非目标

- 秘书自己读写文件、执行命令、调用 MCP。
- 秘书代用户批准权限或回答 `ask_user`。
- 新建 / 克隆项目、SSH 派活、外部事件源（GitHub / IM）。
- 手机精简视图（`packages/phone`）。

## 身份与承载

- 新增 `ProjectKind = 'secretary'`（`src/shared/types/agent.ts`）：Main 幂等登记的隐藏项目，cwd 为 `userData/secretary/workspace/`（空目录），不投影到项目列表。照 `ensureBotHomeProject` / `ensureScratchProject` 的写法（`src/main/services/sourceAuthorityRegistry.ts`）。
- `ConversationAuthority` 增加只由 Main 写入的 `role: 'secretary'`。所有秘书判定只信它，不信 renderer 传入。
- 多个秘书会话都挂在这个隐藏项目下。"秘书身份"即这个隐藏项目：记忆用它的 project 记忆空间，派出关系、点名授权、工作台都按它归属，任一秘书会话都能操作。
- 例行任务用秘书自带的定时（见"定时"一节），不依赖 scheduler 插件。

| 工作方式 | 自主度：派活前先问我 / 派完告诉我 / 完全自主 | 派活前先问我 |
| | 免确认项目：自主度不是"先问我"时，哪些项目可以不经确认直接派活 | 空 |
| | 可见项目：全部 / 勾选 | 全部 |
| | 派出会话模型：跟随项目 / 固定 / 秘书从候选自选 | 跟随项目 |
| | 派出会话 worktree：不开 / 秘书判断 / 总是开 | 秘书判断 |
| | 进行中派出会话上限 | 3 |
| 风格与打扰 | 对你的称呼、回复语言、沟通风格（预设 + 自由补充） | 跟随界面语言、简洁 |
| | 系统通知：仅需要你处理 / 含完成 / 关闭 | 仅需要你处理 |
| | 每日简报时间（自动建一条秘书定时） | 关闭 |

存储：Main 持有 `userData/secretary/profile.json`（原子写），人设补充文字放 `persona.md`，头像放 `avatar.png` + 版本号（同 Bot 头像做法）。不进 `settings.json`，不接入配置 CLI。IPC `secretary:get-profile` / `secretary:save-profile` / `secretary:reset-profile`，入参按 `unknown` 收窄。

生效：名字、人设、模型在下一轮请求生效；自主度、免确认项目、可见项目、并发上限等权限类配置由 Main 在每次工具执行时实时校验，保存即生效。

### 初次设置流程

首次点侧栏秘书入口且无 `profile.json` 时，在主区域（非弹窗，照顾 PWA）展示欢迎页，二选一：

- **表单**：三步。名字与头像 → 模型 → 工作方式；每步有默认值，可"全部用默认，直接开始"。完成后建第一个秘书会话，秘书开场自我介绍。
- **对话**：先用全局默认模型建秘书会话，由秘书提问收集配置。秘书通过 `secretary_profile_propose` 提交配置草案，界面渲染成确认卡片（逐项列出、可就地改），**用户点确认后 Main 才写入**。秘书不能直接改自己的配置，避免它自行提高自主度或扩大项目范围。

两条路径写同一份 `profile.json`。软偏好（工作习惯、别打扰的事）不进配置，写进秘书私有记忆。

### 修改与重来

- 修改：「设置 → 秘书」页复用表单组件；秘书区块的齿轮按钮直达；在秘书会话里说"改一下 xx"同样走 `secretary_profile_propose` + 确认卡片。
- 重来：设置页「重新设置秘书」清空 `profile.json` 后回到欢迎页；默认保留秘书会话与私有记忆，勾选后可一并清空记忆。

现有首次启动向导在远端被跳过（`App.tsx` 中 `!window.electronAPI.remote`），秘书初次设置不能照搬该条件，PWA 完整模式下必须可用。

## 工具集：白名单

现有禁用机制是黑名单，而且只管内置工具：`sessionDisabledTools`（`src/main/services/builtinToolScopes.ts`）按内置工具名过滤；插件工具由 `spawnSession`（`src/main/services/agentHost.ts`）经 `getExtensionPlugins().toolsForSpawn()` 整批下发。整批下发会带进 tgclient 的 `tg_send_message`（以用户本人身份发消息）、github 的评论工具等，所以秘书和 Bot 会话一样整批关掉插件。

秘书会话的装配由 Main 按 `role: 'secretary'` 决定：

- 内置工具：按**全量内置工具目录减去白名单**计算禁用列表，新增内置工具默认对秘书不可见。
- 插件：全部不合并（工具、技能、预设、工作流、hooks、子代理类型）。
- MCP：全部关闭。
- 回归测试：任意未列入白名单的内置工具、任意插件工具，对秘书会话都不可见。

| 类别 | 工具 | 说明 |
| --- | --- | --- |
| 项目 | `project_list`、`project_info` | 只给元数据：名称、类型、路径、当前分支、是否有未提交改动、最近活跃时间。不给文件内容 |
| 会话读 | `session_list`、`session_read` | 跨项目；见下方"会话读的返回范围" |
| 会话写 | `session_create`、`session_send`、`session_stop` | 受可操作范围与自主度约束，由 Main 校验；`session_create` 可带 `goal` |
| 待办 | `todo_item_add` / `todo_item_update` / `todo_item_dispatch` | 工作台「待办」列；dispatch 即转为派出会话 |
| 定时 | `schedule_add`、`schedule_list`、`schedule_remove` | 见"定时"一节 |
| 配置 | `secretary_profile_propose` | 只产出草案，需用户在卡片上确认 |
| 记忆 | `memory_search`、`memory_capture` 等 | 写只能写秘书私有空间；可只读检索全局与各项目空间（受"可见项目"限制） |
| 通用 | `ask_user`、`web_search` / `web_fetch` | 已有 |

明确禁止：bash、read / grep / find / ls、apply_patch、codemode、subagent / workflow、computer、browser 系列（右侧浏览器面板留给用户自己用）、所有 MCP、所有插件工具。

`session_*` / `project_*` 工具由 Main 实现，参数按 `unknown` 收窄；会话、项目只接受 id，路径由 Main 从权威记录推导。

### 会话读的返回范围

`session_read` 返回状态、摘要、待处理审批 / 提问，以及最后 N 条消息里的**用户消息和助手正文**，不返回工具调用参数和工具输出。工具输出里常有网页、文件、命令结果这类不可信文本；秘书能派活，读到这些文本就形成"网页里的一段话让秘书去另一个项目执行命令"的注入链路。秘书需要细节时，引导用户打开该会话查看。

### 只读结果的脱敏与标注

`session_read`、`project_info`、跨项目 `memory_search` 的返回统一经过 `redactSecrets`（`src/main/services/memory/distill.ts`，复用，不另写规则）打码密钥类文本。会话正文和项目记忆包在 `<untrusted-content source="...">` 里返回，系统提示词说明其中的指令一律不执行。

## 自主度与可操作范围

Main 在每次工具执行时校验，不依赖工具描述：

| 自主度 | 目标项目在"免确认项目"中 | 目标项目不在其中 |
| --- | --- | --- |
| 派活前先问我 | 确认卡片 | 确认卡片 |
| 派完告诉我 | 直接创建，回复中告知 | 确认卡片 |
| 完全自主 | 直接创建 | 确认卡片 |

- 确认卡片列出目标项目、首条 prompt 全文、模型、是否开 worktree；用户确认后 Main 才创建。`session_create` 与 `todo_item_dispatch` 同一套规则。
- `session_send` / `session_stop` 对"非秘书派出、且未被点名"的会话一律拒绝。`session_send` 向派出会话发消息不需要确认卡片，因为会话已经存在且在目标项目的审批策略之下。目标会话正在运行时，消息进入该会话现有的排队，不打断当前轮。
- 目标会话有待处理的审批或 `ask_user` 时，`session_send` 拒绝并返回"需要用户处理"。这一条在工具层强制，防止秘书借一条普通消息替用户作答。
- 进行中派出会话达到上限时，`session_create` 返回错误，由秘书转告用户。

### 确认卡片的状态

确认卡片是 Main 持有的一条提案记录，存在 `dispatch.json`，状态只按下面的方向走：

```
待确认 ──确认──▶ 执行中 ──▶ 已创建 / 失败
   │
   ├──拒绝──▶ 已拒绝
   └──超过 24 小时──▶ 已过期
```

- 用户确认时，Main 先把状态从"待确认"改成"执行中"并落盘，再执行。桌面和 PWA 同时点、或同一端连点，只有第一次改状态成功的会执行，其余返回当前状态。
- 执行前**重新校验**：项目仍存在且为本地、可操作范围、进行中上限、worktree 选项。提案生成后到确认前，这些都可能变了。校验不过就记"失败"并给出原因。
- 结果（已创建 / 失败 / 已拒绝 / 已过期）作为一条 `<session-updates>` 进入回传队列，投给发起提案的秘书会话，秘书据此继续，不用等用户再说一句话。
- 配置草案（`secretary_profile_propose`）用同一套状态。

### 点名授权

现在的会话引用只带 `label` 和 `sessionFile`，发送时被序列化成 prompt 正文里的一行文字（`src/renderer/components/chat/mentionComposer.ts`），没有会话 id。秘书不靠解析正文：

- 会话引用补上 `conversationId`；renderer 向秘书会话发 prompt 时，在请求上附带结构化字段 `referencedConversationIds`。
- Main 在 IPC 边界按 `unknown` 收窄，用会话权威逐个校验（存在、非 child、非 bot、属于可见项目），通过的加入秘书身份的授权集合，持久化在 `dispatch.json`。
- 只有发给 `role: 'secretary'` 会话的 prompt 会处理该字段。

## 派出会话的生命周期

现状：普通会话由 renderer 建记录、调用 `agent.spawn` + `agent.prompt`。秘书派活不能依赖某个 renderer 在线，也不能让桌面与 PWA 两端各建一次，所以改为 **Main 原生创建**：

1. 校验目标项目（本地、active）、可操作范围、自主度与 worktree 选项；
2. 在 `SourceAuthorityRegistry` 写入根会话权威，附 `origin: { secretaryConversationId }`；
3. 通过"Main 写会话记录"通道（见下节）把新会话记录写盘并推给所有主界面，id 由 Main 生成；
4. Main 按项目默认值解析模型 / 预设 / 审批模式，调用 `spawnSession`，再以 Main 生成的 `deliveryId` 发首条 prompt；
5. renderer 之后打开该会话时走现有的 attach / 快照路径，不再二次 spawn。实现时第一件事就是真机验证这一条（桌面与 PWA 各一次）。

秘书派出关系、点名授权持久化在 `userData/secretary/dispatch.json`（原子写），重启后据此恢复工作台与回传订阅；正在运行的派出会话重启后按现有会话恢复规则处理，不重放 prompt。

### 派出会话的目标

`session_create` 可带可选参数 `goal`（文字）。带目标的派出会话按现有会话目标语义运行：每轮结束自动续跑，直到模型调用 `goal_complete` 并通过校验、调用 `goal_blocked`，或触发安全限制。

现有续跑由 renderer 会话 store 驱动，Main 侧只有 `pairSessionHost` 在 `isPairHeadless()` 时驱动（`src/shared/pair/headlessQueue.ts`）。派出会话不能依赖某个 renderer 打开它，所以由 Main 为派出会话驱动续跑，复用 `headlessQueue` 的目标信号处理；renderer 打开该会话时只展示目标状态，不再重复续跑。

### Main 写会话记录

`enso-conversations` 目前只由 renderer 写入。`mergeConversationsWrite`（`src/main/services/remoteRenderer/conversationSync.ts`）只负责把一个 renderer 的写入转发给其他主界面；只有一个主界面时直接整表覆盖。Main 插入一条记录后，renderer 如果在收到补丁前写回整表，这条记录会丢。

改法：

- Main 推给主界面的每个补丁带递增 `seq`；Main 为每个 seq 保留应用后的状态，直到所有主界面都确认过。
- renderer 应用补丁后记下最大 `seq`，写回整表时附带它。
- Main 用"该 renderer 已应用到的 seq 对应的状态"与写入值求 diff，再合并进磁盘。单主界面也走这条路径，不再整表覆盖。
- Main 新增记录、renderer 写入都经同一入口串行执行。

测试覆盖：Main 插入后 renderer 用旧状态写回，记录不丢；renderer 应用补丁后删除该记录，删除生效；两个主界面并发写入，结果与单端顺序写入一致。

## 权限边界

- 派出会话沿用目标项目自己的审批策略，秘书不能提权或改审批模式。
- 派出会话的权限审批、`ask_user` 只能由用户处理。秘书在回传里看到"需要用户处理"，只负责转告。
- 秘书只看得到会话的用户消息和助手正文（见"会话读的返回范围"），自主派活只对免确认项目生效。

## 回传

会话空闲不等于事情做成了。回传给秘书的是"结果类型"，不是"完成了"：

| 结果类型 | 触发 | 秘书应该怎么说 |
| --- | --- | --- |
| `goal-complete` | 带目标的会话调用 `goal_complete` 且通过校验 | 已完成，可转告结论 |
| `goal-blocked` | 带目标的会话调用 `goal_blocked`，或触发安全限制 | 卡在哪里、需要什么 |
| `turn-ended` | 不带目标的会话一轮结束且空闲 | 只能说"它停下了，最后说了什么"，不能断言完成；需要时 `session_read` 自己判断 |
| `needs-user` | 出现待审批 / 待回答 | 转告用户去处理 |
| `failed` | 轮次报错、worker 异常退出 | 失败原因 |
| `stalled` | 运行中且超过 10 分钟没有任何 worker 事件 | 可能卡住，建议用户看一眼 |
| `interrupted` | 应用重启时该会话正在运行 | 被中断，是否重派由用户决定 |

- `stalled` 由 Main 每分钟检查一次派出会话得出，同一会话一次运行内只报一次。worker 进程已退出算 `failed`，不算 `stalled`；正在等审批的会话算 `needs-user`，不算 `stalled`。
- 事件按目标秘书会话聚合，秘书空闲时合并注入一条 `<session-updates>` 消息。同一会话的多次事件只保留最新状态；进行中的变化只更新工作台。
- 投递队列参照 `BotSessionHost`（`src/main/services/bots/botSessionHost.ts`）：每条事件有去重键（派出会话 id + 结果类型 + 该会话的轮次序号），同一件事只入队一次。每批最多 20 条、12k 字符，超出的留到下一批。秘书这一轮正常结束才算这批投递成功；这一轮失败时整批重投，最多 6 次，间隔逐次拉长，用完后只留在工作台。
- 目标秘书会话：派活的那个秘书会话。它已归档或删除时，改投最近活跃的秘书会话；一个秘书会话都没有时，只更新工作台和侧栏角标。

## 操作记录

秘书的每个写操作（建会话、发消息、停止、确认卡片状态变化、定时增删、配置写入、点名授权）追加一行到 `userData/secretary/audit.jsonl`：时间、秘书会话 id、操作、目标 id、结果。只追加，不提供界面，用于事后查"秘书到底做了什么"。超过 5MB 时轮转一份。

## 定时

秘书自带定时，不依赖 scheduler 插件。scheduler 插件的 `cron_create` 只注入创建它的会话、只支持重复任务，且插件可能未安装，都不满足秘书需要。

- 存储：`userData/secretary/schedules.json`（原子写），归属秘书身份。
- 工具：`schedule_add`（`at` 一次性 ISO 时间，或 `cron` 五段式本地时间，二选一；`prompt` 必填；`name` 必填）、`schedule_list`、`schedule_remove`。
- 到点后 Main 把 `<secretary-schedule>` 消息放进与回传相同的注入队列，投递目标和改投规则与回传一致；一次性任务投递后删除。
- 应用未运行期间错过的触发：一次性任务在下次启动时补投一次；cron 任务不补投，只算下一次。
- 每日简报和待办到期提醒都是定时的特例，由 Main 生成对应定时，不需要秘书调用工具。
- 设置页「秘书」里列出全部定时，可删除。

```
│     修复 xxx  [秘书]      │  派出会话留在所属项目，带标记
└──────────────────────────┘
```

- 秘书以"置顶伪项目"出现在项目列表第一行：外观与项目行一致，名称和头像取自 `profile.json`，下面列秘书会话，默认最近 3 条，可折叠。与其他项目之间用虚线分隔。
- 无论选中哪个分组标签都显示，不参与项目拖动排序，不能被分进分组。
- 行内操作只有 ＋（新建秘书会话）和 ⚙（秘书设置）；右键菜单只保留这两项与"重新设置秘书"，没有移除项目、在访达中打开、项目设置。
- 这一行由侧栏单独渲染，不是把 `secretary` 隐藏项目投影进项目列表。项目选择器、分组、排序、项目设置等读项目列表的地方都看不到它。

- 折叠侧栏时在图标列最上方放秘书图标 + 角标，点开最近的秘书会话；另设全局快捷键。
- 派出会话不挂到秘书下，跨项目汇总看工作台。
- 不做顶部模式切换（会遮住项目会话），不放进项目分组标签（语义是筛项目）。曾考虑在分组标签之上放独立区块，选了伪项目，因为它与现有项目列表的视觉和操作习惯一致。

## PWA 完整模式

- 会话创建与回传都在 Main，与哪个 renderer 在线无关。
- 新会话记录走"Main 写会话记录"通道；`activeId` 不进共享补丁，PWA 上派活不会切走桌面当前会话。
- 工作台数据走 Main 推送，多端一致；就地审批复用现有审批 IPC。

## 实现顺序

一次合入，放在实验开关后。内部按下列顺序提交，每步的检查通过后再做下一步，把风险最大的底座放在最前面：

1. **Main 写会话记录**：`seq` 补丁与写回合并，连同上面三条测试。
2. **Main 原生派出会话**：先不接秘书，用测试入口在本地项目建会话并发首条 prompt；真机验证桌面与 PWA 打开该会话时都不重复 spawn。
3. **秘书身份与工具装配**：`secretary` 隐藏项目、`role`、内置工具白名单、插件整批关闭；回归测试断言白名单外的工具不可见。
4. **会话与项目读**：`project_*`、`session_list`、`session_read`（只返回用户消息与助手正文，脱敏并标注不可信）。
5. **派活与授权**：`session_create`（含 `goal`）/ `session_send` / `session_stop`、`dispatch.json`、自主度矩阵、确认卡片状态机（重新校验、防重复执行）、`referencedConversationIds` 点名授权、Main 驱动派出会话目标续跑、`audit.jsonl`；可操作范围、自主度矩阵、卡片状态机用单测覆盖。
6. **回传与定时**：事件订阅、结果类型分类、停滞检查、聚合注入、去重与重投、目标秘书会话的改投规则；`schedules.json` 与 `schedule_*` 工具。
7. **配置与初次设置**：`profile.json`、表单与对话两条路径、`secretary_profile_propose`、设置页修改与重来。
8. **记忆**：秘书私有空间读写、全局与可见项目空间只读检索，空间校验放在记忆服务里。
9. **界面**：侧栏入口、工作台（含待办）、记忆面板、"由秘书派出"标记、会话引用跳转。
10. **验收**：至少两家厂商模型真机走通"问进展 → 派活 → 确认 → 回传 → 转告"，桌面与 PWA 各一遍。

对现有功能的改动点限于：会话记录写入合并、`spawnSession` 的秘书装配、会话权威字段、会话引用携带 id、记忆检索的空间可见性、侧栏顶部区块、`SidePanelTabKind`。

## 风险与待验证

- 第 2 步若发现 renderer 打开会话时必然重复 spawn，需要先改 attach 路径，派活相关步骤顺延。
- 秘书长期对话的上下文膨胀：依赖自动压缩 + 秘书记忆；`session_read` 返回量有上限。
- 记忆检索目前按"全局 + 当前项目"决定可见空间，秘书需要按"可见项目"放开只读检索，且写入仍锁在私有空间，需在记忆服务侧校验而非只靠工具描述。
- Main 驱动派出会话目标续跑后，renderer 打开同一会话时不能再续跑一次；需要一个"续跑归属"标记，第 5 步验证。
- `pairSessionHost` 的 `adoptPairSessionHeadless` 已在 Main 接管手机端创建的会话，是 Main 原生建会话的先例，第 2 步先读它。
