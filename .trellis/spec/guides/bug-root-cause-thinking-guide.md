# Bug 根因思考指南

修完一个 bug 之后花五分钟做这件事，避免同一类问题反复出现。

## 先问：症状和根因隔了几层

本仓库已记录的高代价问题都有同一个特征 —— **看到问题的地方不是问题所在的地方**：

| 症状 | 根因所在 |
|------|----------|
| 输入框左边一大片留白 | 组件封装的 DOM 结构（className 落在包裹层） |
| 弹窗里的下拉点开没反应 | z-index 令牌选错 |
| 标题不垂直居中 | 根字号 14px 导致 rem 换算 |
| 去重完全没生效 | "什么算同一个"的定义错了 |
| 启动报找不到 Electron | 构建配置覆盖了默认 external |

所以第一个问题永远是：**这是我改的那层造成的，还是下面某层的默认行为？**

## 根因分类

对号入座，不同类别的防复发手段不同：

| 类别 | 例 | 防复发 |
|------|-----|--------|
| 层边界假设错误 | className 落在包裹层 | 写进 spec 的组件规范 |
| 平台/框架的隐式行为 | `setWindowButtonVisibility` 重置位置 | 写进 big-question |
| 领域定义错误 | 去重指纹用路径而非名称 | 写进 spec 并说明为什么 |
| 配置合并覆盖 | preload 的 external 失效 | 写进 big-question + 判别方法 |
| 数据兼容 | 字段改名导致旧数据失效 | 写进类型规范 |

## 为什么之前的修复没拦住

如果这个 bug 是"改过一次又犯"，重点问这个：

- 之前只修了症状（加大 padding 躲开重叠）而没动根因（rem 换算）？
- 修了一处但同类还有别处（一个 Select 传了 zIndex，另一个没传）？
- 修法正确但没写进 spec，下次换个人又踩？

## 验证要看证据

不要凭"应该修好了"结束。本仓库的验证手段：

```bash
pnpm typecheck && pnpm lint     # 静态
```

行为类问题用真机 CDP 验证：读计算样式、读 IPC 返回值、读 `settings.json`、截图。
改动过用户真实文件的，用 md5 核对源文件是否如预期未变 / 已变。

**验证完清理**：调试端口、测试数据、临时文件。

## 沉淀

排查代价明显超出预期的问题，补一篇到
[../big-question/](../big-question/index.md)，包含四段：

1. **症状** —— 用户/开发者实际看到什么（含误导性的报错文本）
2. **根因** —— 为什么会这样
3. **修法** —— 具体代码
4. **判别方法** —— 下次怎么快速确认是不是这个问题

只是"当时没想到"的普通疏漏不必单独成篇，补进对应层的 spec 即可。
